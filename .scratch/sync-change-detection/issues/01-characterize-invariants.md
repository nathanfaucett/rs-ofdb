# 01 — Characterize correctness and discovery cost

Status: Done

## Purpose

Establish executable evidence before changing interfaces or commit machinery. Read [the specification](../spec.md) first.

## Work

- Trace SQL local/explicit transactions, sync apply, schema cleanup, unique-key conflict tombstones and KV writes/imports to their real commit points. Identify every mutation path that could bypass logical change tracking.
- Inspect existing transaction `changes`, `MutationSummary`, backend commit notification and tests before inventing new bookkeeping.
- Add focused characterization tests for snapshot merge, metadata-only changes, combined metadata/document changes, multi-change incremental payloads, dependency order, failed/rolled-back transactions and snapshot rewriting/compaction.
- Establish how standalone incremental-key labels differ from actual Automerge change identities; test history available inside a snapshot versus separately exportable stored deltas.
- Capture deterministic baseline counts for an established SQL peer reconciling a one-row edit: document reconstruction, snapshot export and history enumeration.
- Record which assumptions pass, which are unverified, and any reproducible existing defects. Do not silently lock an existing correctness defect into the desired contract.

## Acceptance

The mutation-path inventory identifies a safe publication point and conservative fallback for untracked paths. Tests demonstrate the identity/metadata/history cases or expose a concrete blocker. Baseline measurements and the smallest proposed end-to-end slice are recorded under Comments. No production crate moves occur in this issue.

## Validation

Run the relevant existing and new tests for the touched packages with their required features. Final workspace feature-powerset and CRAP validation belongs to issue 05.

### Mutation-path inventory and publication boundary (for ticket 03)

| Path                                                    | Real commit / existing bookkeeping                                                                                                                                                                                                                                                                                                      | Tracking implication and safe fallback                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SQL ordinary statement batches                          | `sql-engine/src/executor.rs::execute_statement` creates one kernel transaction; `execute_in_transaction` accumulates `Vec<Change>`; success commits, error rolls back. `change.rs::apply_local_change` appends only requested/materialized local changes.                                                                               | The vector is neither a complete semantic mutation inventory nor published commit state. Start with changed-table invalidation, not only requested row IDs.                                                                                                                                                               |
| SQL explicit transactions                               | `sql-engine/src/engine.rs::EngineTransaction::{execute,commit,rollback}` retains the same transaction/vector across calls. Execution errors abort commit and cause rollback; drop discards pending work.                                                                                                                                | Publish once for the successful complete write set, never from individual execute calls. A losing optimistic in-memory commit must not publish.                                                                                                                                                                                                                                      |
| Conflict resolution                                     | `engine.rs::resolve_row` calls executor resolution directly, then kernel commit/rollback.                                                                                                                                                                                                                                               | Does not pass through `EngineTransaction.changes`; include it explicitly or fall back to table invalidation.                                                                                                                                                                                                                                                                         |
| SQL incoming state, deltas and public mutation closures | `sql-sync/src/session.rs::apply_received_batch` uses engine state-transfer mutation methods. `sql-engine/src/state_transfer.rs::{mutate_transaction,mutate_tables_validated,mutate_rows}` own commit/rollback after validation and index maintenance.                                                                                   | `MutationSummary` records tables/catalog, not rows. `RowMutation` covers requested old/new rows, not all induced deletes. Public closures can write raw transaction bytes or supply incomplete summaries: unknown writes must force broad reconciliation. Incoming commits must invalidate other peers too.                                                                          |
| Catalog/schema cleanup and drop/recreation              | `sql-engine/src/schema.rs::reconcile_schema_names`, dependent-row cleanup and inactive-index storage removal call codec/transaction mutations directly inside the enclosing transaction. `executor.rs` DDL and `sql-engine-automerge/src/codec.rs` drop/observed-drop helpers change metadata separately from documents.                | Catalog invalidation must expand to all affected dependencies/tables, including tombstoned catalog rows and drops not reflected in heads. | Unique-key/schema-validation side effects               | `sql-engine/src/index.rs::rebuild_table` directly calls `codec.delete_row` for invalid rows and losing unique contenders, including tombstoned claim winners; index updates are derived bytes.                                                                                                                                          | Invalidate the whole affected logical table until exact indirect row collection is proven. | KV incoming snapshots                                   | `KvTransaction::import_snapshot` rejects stale generations, skips known same-generation history, merges divergent histories and replaces/prunes old generations; same commit path as local writes.                                                                                                                                      | Incoming accepted mutations wake fan-out; known history should be silent. Generation replacement invalidates selection for the key. Expiry only changes read visibility, with no timer-generated mutation.                                                                                                                                                                           |
| Physical snapshot insertion/update/compaction           | `btree-automerge/src/{util,compaction}.rs` write or replace storage records in the caller's transaction; SQL `merge_state` rewrites one row to a snapshot.                                                                                                                                                                              | Physical records are not a durable logical/change log. Representation-only compaction need not imply new document history; unknown physical writes must conservatively invalidate.                                                                                                                                                                                                   |
| Redb backend publication                                | `btree-redb/src/transaction.rs::NativeWriteTransaction::commit` computes net physical mutations via `changes.rs::Mutations`, synchronously persists, then calls `ChangeSignal::committed()` before writer admission is released. SQL `RedbKernelTransaction::commit` delegates here; KV Redb B-tree transactions share this strategy.   | This is the safe existing persistence/publication boundary. Extend transaction-owned generic bookkeeping and attach SQL/KV semantics above it; do not add an async post-commit publication gap. Rollback/error/drop do not publish successful commits. Independently constructed wrappers/raw native writes cannot be assumed to share the signal: broad reconciliation is required. |
| In-memory backends and subscription/runtime             | SQL `InMemoryKernelTransaction::commit` checks snapshot revision before replacing state; generic `InMemoryBTreeTransaction::commit` applies its patch, with no committed subscription. `btree/src/changes.rs` supplies coalesced revision wakeups for supporting backends; `sync-runtime/src/subscription.rs` schedules reconciliation. | Backend support is not uniform. New peers need initial full comparison. Do not reuse consume-after-export as a race-safe acknowledgement.                                     |

The synchronous Redb commit boundary makes publication-before-admission-release possible, but cancellation around commit, injected durable-commit failure, in-flight acknowledgement races, overflow/gaps and bounded per-peer logical identity state are **not established** by this characterization. Those are ticket 03 acceptance work, not existing guarantees. No production publication strategy is changed here.

### Executable results and history interpretation (for ticket 02)

- `crates/sql-engine-automerge/tests/change_detection.rs`: concurrent snapshot merge preserves both independently edited columns; SQL rollback, aborted explicit transaction and optimistic commit conflict preserve committed state. Metadata-only deletion leaves document bytes/history unchanged while changing the manifest. Full-state apply merges combined concurrent history and deletion metadata without resurrection.
- The same suite verifies topological inventory order against actual Automerge dependency hashes, rejection/rollback of a child without its parent, recovery with a payload containing both changes, and inventory of both actual hashes even though the bundled payload is stored under only its last hash. Its first change is not separately exportable.
- SQL snapshot rewriting retains full Automerge history and equivalent manifest digests across compressed/uncompressed encodings, while `export_change` returns `None` for snapshot-contained IDs. This is an export limitation, not lost history; ticket 02 can export native history or preserve the existing full-state fallback.
- `crates/btree-automerge/tests/change_history.rs`: one `update` creates two Automerge changes in one stored incremental. Its label equals `hash_heads(heads)` and is not any individual change hash. Explicit compaction reduces snapshot-plus-delta records to one snapshot while preserving all three original changes and heads. SQL local `merge_row` instead stores an individual change under its actual hash: these labels are not interchangeable.
- `crates/kv-store/tests/change_detection.rs`: a multi-write commit produces a coalesced wakeup independently observable by two subscribers; precommit, rollback, dropped transactions and read-only commits are silent. Incoming snapshot commit wakes fan-out; duplicate history and read-time expiry do not. Failed import followed by caller rollback preserves prior values and publishes nothing.

### Reproducible existing defect — repair in ticket 04

`incremental_reconciliation_transfers_combined_document_and_deletion_metadata` is deliberately ignored with the defect and destination ticket in its reason. Reproduction: bootstrap two peers; update one row's document; delete it on the same source before the next session; reconcile. The receiver incorrectly retains a visible row. The ordinary live suite reproduced this failure before the ignore attribute was added; the explicit `--ignored` command below was also run and failed at the receiver-visibility assertion (exit 101), confirming the retained regression. Run explicitly with:

```sh
cargo test -p ofdb-sql-engine-automerge --test change_detection incremental_reconciliation_transfers_combined_document_and_deletion_metadata -- --ignored --nocapture
```

`sql-sync/src/session.rs` outbound selection sends `SyncIncrementalChange` with document payloads, without the row's deletion metadata, when missing deltas are exportable. A heads-and-metadata mismatch must not select a document-only path. The passing full-state combined-history test demonstrates a correctness fallback; ticket 04 should carry metadata or force a state unit, remove the ignore, and keep the engine's validated apply path. Do not bless the current behavior or silently drop this regression during ticket 02's interface rewrite.

### Deterministic discovery baseline and smallest slice

Fixture: one table (`people`, three columns), eight rows; two initially synchronized in-memory SQL engines using the real Automerge codec; update one row; reset counters; reconcile again. Counters are test-only decorators of public `SyncRowCodec` methods, summed over both peers and including catalog work. No timers or production hooks are used.

| Observation                                     | Baseline |
| ----------------------------------------------- | -------: |
| Full snapshot export calls                      |       49 |
| History inventory/enumeration calls             |       26 |
| Nonempty snapshot digest loads                  |       48 |
| Traced reconstruction/load attempt lower bound  |      123 |
| Source state frames / incremental change frames |    0 / 1 |

The lower bound is `export_state + change_inventory + nonempty manifest_digest`: the current real codec reconstructs a document in each of the first two methods and reloads a saved document in the third. It is **not** a global count of all private reconstruction calls; catalog decoding, apply/validation and other internal work can add more. Snapshot exports include attempted absent-state exports. The test reports the exact baseline and asserts broad discovery still touches both peers' eight rows; an eventual selective implementation should replace these baseline expectations with improvement budgets, not preserve broad work.

Smallest next end-to-end slice: established SQL peers, one local user-row edit with no catalog change; obtain history summary and metadata from one read transaction (02), select the committed row/table invalidation with independent bounded consumer progress (03), compare/send missing native history through existing validated apply and retain metadata/full-state fallback (04). Keep reconnect/new-peer/catalog/unknown paths broad; do not claim local subscriptions alone detect remote-only commits.
