## Reproduced baseline and root cause

At parent 1f0fe5a, restore the public native conflict regression's final incremental `Database::synchronize` exchange instead of whole-state reconciliation. A first single run passed; a subsequent five-run baseline produced **3 passed / 2 failed** with `RemoteAbort("Error: Incremental change hash does not match key (data change batch)")`. New public native-to-memory sequential/concurrent update fixture produced **1 passed / 4 failed** in five baseline repetitions, with `Engine(Custom("Incremental change hash does not match key"))` before explicit resolution. These counts are from the final summarized baseline repetition command; earlier exploratory repetitions are not conflated with them. Baseline implementation was unchanged; only regression tests added/restored.

Two interacting implementation defects:

1. `AutomergeRowCodec::encode_row/encode_resolution` reconstructed snapshot plus incremental history, then used `AutoCommit::save_incremental`. Installed Automerge 0.10's `load_incremental` does not update its save cursor; reconstruction therefore causes subsequent saves to include already persisted history. `merge_row` identifies the newly authored change but stores the bundle under that single hash. The deterministic public Engine/SyncRowCodec regression `sequential_updates_export_only_the_identified_change` failed with `LeftoverData` parsing the exported second payload as one change. Capture actual pre-update heads and use existing `save_after(&previous_heads)` for both ordinary writes and explicit resolution. No dependency or abstraction needed.
2. `build_outbound` obtained the codec's causal inventory but sorted changes by opaque hash ID. A dependent change could precede its prerequisite. Temporary trace after the first fix showed the payload's actual hash matched its advertised ID, but the change was not in the applied history (Automerge queued it for missing dependencies). The unchanged receiver then correctly failed its newly-applied hash check. `incremental_session_preserves_dependency_order_not_hash_order` generates sequential changes until the inventory contains an explicit hash-order inversion (bounded at 256 updates), so the regression exercises the defect independent of random actor ordering. It failed with the same RemoteAbort before the ordering fix. Stable-sort by catalog/table/row only, preserving dependency order within each row. Receiver grouping retains strict row ordering and rejects duplicate IDs using a per-row set; hash order is not causal validity. Document existing `SyncRowCodec::change_inventory` ordering contract.

The intermediate sender-only ordering fix caused the new session test to time out (300s, then smaller diagnostic runs): the old receiving-side hash-order guard rejected the causal sequence, and the joined fixture retained channel handles while its other role waited. This was not reported as a pass. Updating the receiving guard as part of the same root-cause fix made the test complete. Temporary tracing was removed. Final ordering regression uses **one unit per frame**, exercising causal delivery across frames.

`apply_change` and its hash validation are **unchanged**. No final-document hash-membership bypass, forged-payload acceptance, new timers, domain selection policy, backend API escape, feature or dependency change. Existing duplicate-apply and rollback semantics remain. Public Database/Client/Transaction signatures from 07 are unchanged. The wire message schema/version is unchanged; receiving implementations must use the repaired causal-order semantics rather than old lexical hash ordering. No old-version compatibility wrapper or persisted-history migration is introduced; pre-fix stored overlapping-bundle upgrade scenarios were not qualified.

## Public regressions and security behavior

- Engine/SyncRowCodec test exports two sequential native updates, parses each as exactly one Automerge change, independently checks its hash against the exported ID, rejects a batch whose second ID carries the first payload, verifies manifest unchanged after rejection, then applies valid and duplicate batches to convergence.
- Public `ofdb_sql` native-to-memory fixture makes divergent false/true and alice/bob writes, including false then true on the same peer before exchange. All concurrent values survive incremental sync. Explicit partial false resolution leaves ownership ambiguous, synchronizes after native reopen, converges to exact exported state, then reopens again with unresolved ownership intact. Storage never chooses security policy itself.
- Existing native fixture now uses real incremental sync after resolution/reopen, not whole-state fallback. Existing invalid/duplicate/nonconflicted/primary-key/malformed/missing resolution rejection, partial resolution, native persistence, and tombstone protection remain active.
